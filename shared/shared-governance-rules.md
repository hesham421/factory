# ERP GOVERNANCE — SHARED GOVERNANCE RULES
## Operational Rules — Embedded in Every Project

```
File ID        : SHARED-GOVERNANCE-RULES
Version        : 2.0 — Backend/Frontend Split + PRD/UI-UX Integration
Status         : MANDATORY — Embed in every project's system prompt
Companion to   : SHARED-GOVERNANCE-CORE.md (foundations)
                 SHARED-ARTIFACT-CONTRACTS.md (artifact interface rules)
Maintained by  : Architecture Authority
```

The Shared Governance Core (SHARED-GOVERNANCE-CORE.md) defines foundations:
truth layers, principles, vocabulary, and the universal continuation protocol.

This file defines OPERATIONAL RULES: what each project does and does not do,
how projects interact, what constitutes a governance violation, and the
enforcement behaviors every engine applies at runtime.

Both files are embedded in every project. Neither references the other —
both are present.

# SECTION 1 — CROSS-PROJECT COORDINATION RULES

**RULE-1 — Artifact Authoritative Order**

Every project treats artifacts generated by prior projects as
AUTHORITATIVE SOURCES OF TRUTH. The pipeline order governs consumption
(REWRITTEN, v2.1 — see CORE-2 for the full diagram):

```
Project 1   consumes: governed module-registry + business-policies
                       (Project 0) PLUS governed prd.md (Project 0.5)
                       — a HARD GATE, not optional (CONTRACT-10)
Project 2   consumes: governed srs.md (from Project 1)
Project 2.5 consumes: governed prd.md (Project 0.5) ALONE to START
                       (runs in parallel with Project 1) — then
                       reconciles against governed srs.md B1-B4 (Project
                       1) at a gate before human approval (CONTRACT-11)
Project 3.1 consumes: governed srs.md + governed db-script.md
Project 3.2 consumes: REAL API Docs (post-implementation) + governed
                       Project 2.5 outputs (human-approved) + srs.md —
                       NEVER Project 3.1's internal DOC-1 artifact
Project 4.1 consumes: ALL governed artifacts from Projects 0, 0.5, 1, 2,
                       3.1 (platform-summary + module-registry +
                       business-policies + prd.md + srs.md + db-script.md +
                       backend-execution-plan.md + backend-test-plan.md
                       + test-execution-manifest.md)
Project 4.2 consumes: ALL governed frontend artifacts + the Project 4.1
                       report + real API Docs + prd.md + flow-diagram.md
                       + ui-ux-spec.md
Project 5   consumes: test-execution-manifest.md (Project 3.1) + real
                       API Docs — never backend-execution-plan.md /
                       backend-test-plan.md directly except as a
                       documented degraded-mode fallback
```

No project silently reinterprets, regenerates IDs differently,
recreates mappings, changes previous truth layers, or overrides
authoritative outputs. When a project disagrees with an upstream
artifact: raise an OQ-ID (pre-audit) or a Finding-ID (post-audit,
i.e. at Project 4.1 or 4.2). Never resolve the disagreement by
silent interpretation.

**RULE-2 — No Cross-Project ID Namespace Duplication**

ID namespaces are exclusive. Each project creates IDs only in namespaces
it owns. Any ID created in a foreign namespace is a governance violation.

```
Project 0    owns: AQ-ID, INF-ID, BLK-ID
Project 0.5  owns: US-ID
Project 1    owns: ENTITY-ID, RULE-ID, OQ-ID, LOV-ID, SCR-ID, API-ID
                    WORKFLOW-ID (exception-only — see RULE-13)
Project 2    owns: DBF-ID, DBS-ID, XM-[MOD]-ID
Project 2.5  owns: no governance IDs — descriptive/visual output only
Project 3.1  owns: FIELD-ID, ERR-ID, PLAN-ID, DRV-ID, TC-BE-[MOD]-ID
Project 3.2  owns: TC-FE-[MOD]-ID (references FIELD-ID/ERR-ID only)
Project 4.1  owns: Finding-IDs (4A-BE-[A]-[S])
Project 4.2  owns: Finding-IDs (4A-FE-[A]-[S])
Project 5    owns: no governance IDs — script/report generation only
Shared (RXE): RXE-[MOD]-ID (target module space, initiated by Registry)
```

**RULE-3 — No Cross-Project Canonical Reproduction**

Each canonical artifact is embedded once at its owner. All other projects
reference by ID — never reproduce the content. Examples:

- DB Field Traceability Matrix: owned by Project 2. Project 3.1 cites
  DBF-IDs — it does not reproduce column names or DB types.
- Error Catalog: owned by Project 3.1. Project 3.2 (F3) and Projects
  4.1/4.2 reference ERR-IDs — none reproduce error message text.
- OQ Log: owned by Project 1. All artifact headers show count + pointer
  only — never OQ status or question text. This includes OQs raised by
  the Project 2.5 Reconciliation Gate.
- INT Summary: owned by Project 3.1. ALIGN-BE Table 4 confirms gate
  conditions in three rows — it does not reproduce the INT Summary table.
- test-execution-manifest.md: owned by Project 3.1. Project 5 references
  its pre-computed dependency order and RULE→ERR→TC triples — it does
  not re-derive them independently (see CONTRACT-13).

**RULE-4 — Conflict Resolution Protocol**

When two artifacts disagree, the higher Truth Layer governs:

```
Layer 0 (Architecture) governs Layer 0.5a/0.5b (PRD/UI-UX) governs
Layer 1 (SRS) governs Layer 2 (DB) governs Layer 3.1 (Backend Plan)
governs Layer 3.2 (Frontend Plan) governs Layer 4.x (Artifacts)
governs Layer 5 (P5 verification)
```

Special case — PRD/UI-UX vs SRS: SRS (Layer 1) always wins. The
PRD/UI-UX side is marked BLOCKED-BY-OQ, never silently adjusted to
match (see CONTRACT-11's Reconciliation Gate and Resolution Authority Rule).

The detecting project raises the conflict as a formal record and stops.
It does NOT choose an interpretation. Choices belong to the human
architecture authority, documented as an OQ resolution or governance waiver.

**RULE-5 — Single Entry Gate Per Mode**

Each mode has exactly one entry gate. One interaction. All checks in
one view. Confirmation given once. Splitting one gate into sequential
confirmation blocks is a governance overhead violation.

**RULE-6 — XM-ID is the Only Cross-Module Dependency Identifier**

Format: `XM-[MODULE-PREFIX]-[SEQ]`
Example: `XM-FIN-001`, `XM-PRC-002`

CMF-ID and INT-ID are retired permanently. Legacy artifacts referencing
those IDs treat them as equivalent XM-IDs for governance purposes.
New artifacts use only the qualified XM-ID format.
Unqualified XM-IDs (`XM-[SEQ]` without module prefix) are a DRIFT
finding in new artifacts (MAJOR severity). XM-IDs are exclusively a
Backend (Project 3.1) concern — Project 3.2 never assigns or resolves them.

**RULE-7 — GOVERNANCE REDUCED is Explicit and Reversible**

GOVERNANCE REDUCED is declared explicitly in the artifact header and
the Module Governance Index when a pipeline runs without a DB Script.
It is NOT a silent default. It is NOT a permanent state.

Recovery: when DB Script arrives, GOVERNANCE RECOVERY protocol activates
per db-governance-engine.md Section 2.3. The pipeline does not restart
from zero — it upgrades from the last safe gated position.

**RULE-8 — No Optional Pipeline Stages**

```
P(-1) → P0 → P0.5 → P1 → P2 → P3.1 → P4.1 → IMPL-BE → API-DOC-GEN → (∥ P5)
                 ∥
                 └→ P2.5-draft (from prd.md, parallel with P1) →
                    RECONCILIATION GATE (once srs.md ready) → human
                    approval  ─────────────────────────────────────┐
                                                                    ▼
                              GATE: BACKEND MODULE COMPLETE (needs: IMPL-BE
                              done + API-DOC-GEN done + UI/UX approved)
                                                    ↓
                                            P3.2 → P4.2 → IMPL-FE
```
NOTE: The Reconciliation Gate + human approval only need to finish
before P3.2 starts (at GATE: BACKEND MODULE COMPLETE) — they do NOT
block P2 or P3.1. This preserves real parallelism: P2/P3.1/backend
implementation can proceed while UI/UX reconciliation and approval
happen on their own timeline, as long as both finish before P3.2.

NOTE: MODE 4B is abolished. Project 4 runs TWICE — P4.1 (before Backend
implementation) and P4.2 (before Frontend implementation). Both are
pre-implementation gates. Neither is, individually or together, a
post-implementation audit stage.

Any stage skipped requires a documented GOVERNANCE EXCEPTION with formal
acceptance. Skipping is not a shortcut — it is a tracked deviation. The
Backend Module Complete gate (before P3.2) may never be skipped or
approximated with a partial backend — see CONTRACT-12.

**RULE-9 — SOFT-READ Dependencies Are Governed**

Any module that reads from another module's table at the application
layer — without a FK constraint — must declare that dependency as
`XM-[MOD]-[N] Type: SOFT-READ` in its XM Register and INT Summary.

SOFT-READ dependencies carry the same ecosystem coupling risk as FK
dependencies. Undeclared SOFT-READ dependencies detected by the audit
engine are ORPHAN findings (MAJOR severity).

**RULE-10 — Shared Entities Have One Canonical Owner**

An entity declared SHARED in master-registry.md has exactly one
owner-module. Consumer modules reference it by the owner's canonical
ENTITY-ID — they do not assign new ENTITY-IDs for the same entity.

Changes to a SHARED entity by the owner trigger XM RESOLUTION EVENT
notifications to all dependent modules.
(See xm-resolution-event-protocol.md)

**RULE-11 — Module Governance Index Is Maintained by Project 3**

All projects update the MGI at gate completion.
Project 3 (both PASS 1 and PASS 2) is the MGI Maintenance
Authority — responsible for accuracy and staleness detection.

Staleness threshold:
- Active development: 7 calendar days
- Maintenance mode: 30 calendar days

Any project reading an MGI older than the threshold must emit a
staleness warning before acting on its state.

**RULE-12 — XM Resolution Events Are Mandatory Governance Records**

When a pipeline event satisfies an XM dependency unblock condition
for another module, a formal XM Resolution Event (RXE) is created.
RXEs are traceable, auditable governance records — not informal
inter-team communications. RXEs apply exclusively within Backend
(Project 3.1) scope.
(See xm-resolution-event-protocol.md)

**RULE-13 — Workflow Engine Absence Declaration (REVISED, v2.4 — two-tier exception)**

```
هذا النظام لا يحتوي على Workflow Engine من أي نوع، بشكل افتراضي.

الافتراضي في كل موديول ("OFF by default"):
  لا workflow — لا approval flow — لا workflow infrastructure
  P1 لا يُنشئ WORKFLOW-IDs بشكل افتراضي
  P3.1 لا يُنشئ Workflow Service أو Workflow Engine بشكل افتراضي
  P4.1/P4.2 لا يتحقق من Workflow compliance بشكل افتراضي
  ALIGN-BE/ALIGN-FE Gate لا يتضمن "Workflow diagrams exist" check بشكل افتراضي

v2.4 — التغيير الجوهري عن النسخة السابقة: الحظر لم يعد نهائياً بلا أي
مسار. "محرك Workflow حقيقي" (BPMN/Camunda/محرك عام) أصبح مسموحاً به
عبر استثناء معماري موثّق من الفئة الثانية (Tier 2) أدناه — وليس ممنوعاً
مهما طُلب كما كان سابقاً. هذا يبقي الافتراضي "لا يوجد" مع فتح مسار حقيقي
عند الحاجة الفعلية، بدل قانون دائم لا يقبل الاستثناء.
```

**بروتوكول الاستثناء Tier 1 — Module-Specific Approval Flow (بلا تغيير):**

```
الشرط   : طلب صريح من المستخدم لـ approval flow لموديول محدد

الإجراء :
  P1   → يُضيف WORKFLOW-ID ويُوثّق الاستثناء في Section ⓫
         يُدرج في General Notes:
         "Approval Flow بطلب صريح — استثناء RULE-13 Tier 1 — تاريخ [X]"
  P3.1 → ينفّذ كود مخصص خفيف لذلك الموديول فقط (backend)
         لا Workflow Service مشترك
  P3.2 → إن احتاج تمثيل UI للموافقة، يُبنى كشاشة عادية عبر F1،
         لا كمحرك سير عمل
  P4.1/P4.2 → يتحقق من تطبيق الاستثناء بشكل صحيح ومعزول

لا يتجاوز استثناء Tier 1 حدود الموديول الواحد.
لا يُنشئ بنية تحتية مشتركة أو قابلة للإعادة.
```

**بروتوكول الاستثناء Tier 2 — Full Workflow Engine Adoption (NEW, v2.4):**

```
الشرط   : قرار معماري صريح من المستخدم/سلطة العمارة بتبني محرك Workflow
          حقيقي على مستوى المنصة بأكملها — وليس طلباً لموديول واحد.
          هذا استثناء أثقل من Tier 1 ويُعامل كتعديل على القيم المصرح بها في GOVERNANCE-CONFIG.md (وفق قاعدة CORE-8 — Platform
          Stack Declaration) نفسه، لأن إضافة محرك Workflow هي إضافة
          تقنية جديدة للـ stack، لا مجرد كود لموديول.

المتطلبات (كلها إلزامية قبل أي توليد):
  1. طلب صريح مكتوب من المستخدم يسمّي المحرك/القدرة المطلوبة
     (مثال: "أريد اعتماد Camunda كمحرك Workflow للمنصة").
  2. توثيق GOVERNANCE EXCEPTION رسمي (نفس آلية RULE-8) — معتمد باسم
     سلطة العمارة (human architecture authority)، وليس قراراً آلياً
     من أي محرك حوكمة بمفرده.
  3. تحديث GOVERNANCE-CONFIG.md / platform-summary.md لإضافة المحرك المعتمد كجزء
     من الـ stack الرسمي للمنصة (نفس منطق DB_TARGET — قرار يُعلن
     مرة واحدة ثم يُطبَّق باستمرار من قبل كل المحركات).
  4. تحديث master-registry.md بسجل القرار (Registry Event Log).

الإجراء بعد الاستيفاء:
  P0   → يُثبّت المحرك المعتمد في platform-summary.md كجزء من الـ stack
  P1   → يُنشئ WORKFLOW-IDs بحرية عبر الموديولات التي تحتاجها فعلاً
  P3.1 → يُنشئ Workflow Service/Engine integration حقيقي (backend)
  P3.2 → يُنشئ واجهات تمثّل حالة الـ workflow الفعلية عبر F1/F2
  P4.1/P4.2 → يتحقق أن كل استخدام للمحرك يعود لهذا الاستثناء المُسجَّل
              — أي استخدام غير مرتبط بسجل Tier 2 موثّق = مخالفة (انظر
              HR-9 أدناه، تبقى المخالفة CRITICAL لأي محرك غير موثّق)

Tier 2 قرار على مستوى المنصة بأكملها — لا يُطلب أو يُلغى لكل موديول على
حدة، ولا يُستنتج ضمنياً من طلب Tier 1 السابق.
```

**RULE-14 — PRD Is Never a Specification (REVISED, v2.1)**

Project 0.5 output is a NEED, never an enforceable RULE. No downstream
project treats a user story's phrasing as a pre-approved implementation.
See CONTRACT-10 and CORE-5 RULE-12.

v2.1 clarification: Project 1 is now HARD-GATED on prd.md's *existence*
(CONTRACT-10) — this rule is about content authority, not gating, and
the two are independent. Gating P1 on whether prd.md is attached does
NOT relax this rule: a US-ID still can never be cited as sole
justification for a RULE-ID/ENTITY-ID/API-ID decision.

**RULE-15 — Frontend Planning Requires Real Contracts (new, v2.0)**

Project 3.2 never begins on the strength of Project 3.1's internal
planning artifact (DOC-1) alone. It requires the GATE: BACKEND MODULE
COMPLETE — real API Docs + human-approved UI/UX — per CONTRACT-12 and
CORE-5 RULE-13.

**RULE-16 — UI/UX Draft-Then-Reconcile Is Bounded Rework, Not Restart (new, v2.1)**

Project 2.5 starts from prd.md alone, in parallel with Project 1 —
it does not wait for srs.md (supersedes the v2.0 "wait for both"
design). Once srs.md is available, the Reconciliation Gate
(CONTRACT-11) runs before human approval, flagging only the specific
screens/sections that drifted from PRD-only assumptions. Reconciled
sections are never regenerated wholesale — rework is always scoped to
what the Gate actually flags.

# SECTION 3 — HALLUCINATION RESISTANCE RULES
═══════════════════════════════════════════════════════════════════

These rules specifically constrain AI generation behavior to prevent
non-deterministic output that undermines governance integrity.

**HR-1 — No Invention Beyond Source Artifacts**

Every element generated by any project must trace to an uploaded
artifact. If a claim, entity, field, rule, or API cannot be traced
to srs.md, db-script.md, or a prior gated artifact — it must be
documented in the Derivation Log (DRV-ID) before it appears in
any phase output. Undocumented inference is a governance failure.
This applies equally to Project 0.5 (US-ID must trace to P0 content)
and Project 2.5 (flow-diagram/ui-ux-spec must trace to PRD+SRS).

**HR-2 — B2 Repository Strategy Constraint**

Every B2 API must specify a Repository Strategy block with five
mandatory fields: DB Operation type, Join strategy, Transaction
boundary, Fetch strategy, Bulk operation flag.

Any deviation from defaults (NONE join, READ_ONLY, LAZY, no bulk)
requires a DRV-ID entry. No repository pattern is invented without
a documented rationale. This prevents implementation strategy drift
across sessions for equivalent API types.

**HR-3 — F2 Service Contract Constraint**

Every F2 service method must specify: Observable type, Error handling
(ERR-IDs), Loading state (LOCAL/GLOBAL/NONE), Caching strategy, and
XM-ID impact if applicable.

Non-default configurations (GLOBAL loading, non-NONE caching) require
DRV-ID entries. This prevents service layer divergence across sessions.

**HR-4 — ALIGN Table 5 — Presence Only**

ALIGN-BE Table 5 checks FIELD-ID presence across backend phases (✓/⏸).
It does NOT check type consistency — that is P4.1 CHECK-3's scope.
An ALIGN-BE session that performs type checking instead of presence
checking is scope-violating and must be corrected.

**HR-5 — No ERR-ID Invention in F3 or TC**

F3 and TC reference ERR-IDs from the canonical Error Catalog only.
No ERR-ID is invented in F3 or TC (backend or frontend test-plan). If
an error condition is needed that is not in the catalog: Error Catalog
Amendment Protocol activates (execution-governance-engine.md Section
10) — and, since the Error Catalog is Backend-owned, a gap discovered
during PASS 2 (F3) escalates back to PASS 1, it is never invented
locally. The session pauses until the ERR-ID is formally assigned.

**HR-6 — No ENTITY-ID Invention for Shared Entities**

If master-registry.md declares an entity as SHARED, no project invents
a new ENTITY-ID for it. The canonical ENTITY-ID from the registry is
used verbatim. Creating a duplicate ENTITY-ID for a known SHARED entity
is a DUPLICATE governance finding (CRITICAL severity).

**HR-7 — Derivation Log Completeness — Mechanical Checks**

The Derivation Log is not self-validating. P4.1 CHECK-3/5 applies
mechanical checks:
- DRV-ID sequence continuity (no unexplained gaps)
- Every B2 Repository Strategy deviation has a DRV-ID
- Every F2 non-default configuration has a DRV-ID

These checks can be performed without relying on the AI's self-assessment.

**HR-8 — No Stack Substitution**

No project may generate, suggest, or reference a technology outside
the stack declared in GOVERNANCE-CONFIG.md (the rule that requires
this is CORE-8). Generating DDL for a database engine other than the
declared DB_TARGET, or backend/frontend/mobile code outside the
declared BACKEND_STACK / FRONTEND_STACK / MOBILE_STACK, is a
governance violation (CRITICAL severity — STACK VIOLATION type).
See GOVERNANCE-CONFIG.md for the current values and per-dialect
violation examples.

**HR-9 — No Workflow Engine Invention (REVISED, v2.4 — two-tier exception)**

No project may generate Workflow Engine infrastructure of any kind
(see RULE-13) unless ONE of the two RULE-13 exceptions is formally
recorded:

- A light, module-scoped WorkflowService/ApprovalEngine bean, or a
  module-specific approval code path, requires a Tier 1 exception
  (Module-Specific Approval Flow) declared for that specific module.
- A real, generic Workflow Engine (BPMN process, Camunda or
  equivalent, configurable approval framework) requires a Tier 2
  exception (Full Workflow Engine Adoption) — a platform-level
  GOVERNANCE EXCEPTION amending the stack declared in GOVERNANCE-CONFIG.md (CORE-8), never inferred from a Tier 1
  request.

Generating either kind of Workflow Engine infrastructure without its
matching exception recorded is a governance violation (MAJOR severity
— SCOPE VIOLATION type for a Tier-1-eligible case; CRITICAL severity
for a full engine with no Tier 2 record at all, per RULE-13's
"Undocumented/Silent Workflow Engine" row).

**HR-10 — No PRD-as-Specification Drift (new, v2.0)**

No project treats a US-[MOD]-ID's wording as a pre-approved RULE-ID,
API-ID, or SCR-ID. A user story motivates SRS content; it never
substitutes for it. Any generated artifact that cites a US-ID as the
sole justification for a functional decision (instead of a RULE-ID/
ENTITY-ID/API-ID) is a BOUNDARY VIOLATION (MAJOR severity).

**HR-11 — No Frontend Planning on Unstable Contracts (new, v2.0)**

Project 3.2 never begins, and no other project ever supplies it
content, on the basis of Project 3.1's internal DOC-1 artifact.
Real API Docs (post-implementation) are the only acceptable source.
Violation: SEQUENCE VIOLATION, CRITICAL severity (see CONTRACT-12).

═══════════════════════════════════════════════════════════════════

A governance violation is any action that contradicts a rule in this
file, SHARED-GOVERNANCE-CORE.md, or the project-specific governance
engine. Violations are detected at gates and audits and classified:

```
Canonical reproduction         │ ALIGN / P4.1 / P4.2   │ MAJOR

Undocumented inference         │ ALIGN / P4.1-5        │ MAJOR

Scope boundary violation       │ ALIGN / P4.1 / P4.2   │ MAJOR

SOFT-READ not declared         │ P4.1 CHECK-1          │ HIGH (ORPHAN type)
```

**REG-2 — Write Only Via Registry Update Schema**

Every write to master-registry.md uses the canonical REGISTRY UPDATE
block format (see MASTER-REGISTRY-SCHEMA.md Section 12).
No free-form edits. No partial blocks. Block is applied in full or
held pending conflict resolution.

**REG-3 — Registry Update Cascade**

When a DBS-ID is confirmed (P2 gate passed):
The Registry Maintainer evaluates all DEFERRED XM-IDs in the Global
XM Dependency Index targeting the newly gated module. Where conditions
are met: XM RESOLUTION EVENT created. (See xm-resolution-event-protocol.md)

This cascade is NOT automatic — the Registry Maintainer applies it.
But it is mandatory — no DBS-ID confirmation is complete until the
cascade evaluation is documented.
