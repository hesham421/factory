## 1 — WHY STAGE 2 EXISTS

The governance engines (P(-1)–P4) and the Test Generation Engine produce
text artifacts (`platform-summary.md`, `prd-[MOD].md`, `srs.md`,
`db-script.md`, `flow-diagram.md`, `ui-ux-spec.md`,
`backend-execution-plan.md`, `frontend-execution-plan.md`,
`P4.1-audit-report.md`, `P4.2-audit-report.md`, and — from the Test
Generation Engine — `backend-test-plan.md`, `test-execution-manifest.md`,
`frontend-test-plan.md`). For a mid-complexity module these artifacts can
reach thousands of lines (a real pre-v2.0 `test-plan.md` for module ORG
measured 1264 lines containing 104 TCs — now split across
`backend-test-plan.md` and `frontend-test-plan.md`).

Two problems emerge once a module's artifacts are finalized:

```
PROBLEM 1 — Repository organization
  Where do finalized artifacts live? How are they archived per module,
  per version, without manual file-juggling?

PROBLEM 2 — Context window cost for downstream agents
  An implementation agent (Claude Code) that only needs
  API-ORG-014 should not have to load an 8000-line backend-execution-plan.md
  to find it.
```

Stage 2 solves both — without touching what the engines generate. It is a
**packaging and archival layer**, not a content-generation layer.

## 2 — TWO-PART DESIGN

```
PART A — Marker Governance (lives INSIDE the generating engine)
  The engine embeds HTML comment markers into execution-plan.md and
  test-plan.md AT GENERATION TIME, per PROJECT-3-REGISTRY.md Section 5.7.
  For execution plans this is a P3.1/P3.2 responsibility; for test plans
  it is now the Test Generation Engine's responsibility. Either way it is
  NOT a Stage 2 script.

PART B — Artifact Packaging & Archival (Stage 2 tooling — this document)
  Independent Python scripts that:
    1. Create the canonical folder structure for a module (Agent 1)
    2. Archive generated artifacts into that structure (Agent 2)
    3. Read the markers the engines embedded and split artifacts into
       smaller, addressable package files (Agent 3)
```

Stage 2 tooling is entirely dependent on Part A. If the marker syntax in
PROJECT-3-REGISTRY.md Section 5.7 changes, Stage 2 tooling must change in
lockstep — they are coupled by contract, not by accident.

the standard library. They run locally (typically on macOS via Terminal,
Claude Code) — they are NOT Claude Projects and do
NOT call any LLM API. They are deterministic file operations only.

## 3A — STANDALONE VALIDATION MODE (AMEND-P3-M, NEW)

```
Usage: python3 agent3_splitter.py --validate-markers --file <path>

Purpose: run marker_parser.py's structural validation against ONE
         execution-plan.md or test-plan.md file directly, without
         requiring the module's governance-repo folder structure to
         exist first (i.e. no prior agent1_create_structure.py run
         needed). This is the closing-step check referenced by the
         STRUCTURAL SELF-CHECK in PROJECT-3-BACKEND-ENGINE.md /
         PROJECT-3-FRONTEND-ENGINE.md (for the execution plans) and by
         the equivalent self-check in PROJECT-TEST-GENERATION-ENGINE.md
         (for the test plans) — run it against the freshly generated
         file before declaring it complete, not only later during full
         archival.

Checks performed (same engine as the full Stage 1 parse, scoped to
one file):
  ✓ Every PHASE marker has a matching START/END pair
  ✓ Every {KEY} in a PHASE marker is one of the canonical keys for
    that file (per PROJECT-3-REGISTRY.md Section 5.7.3 — file identity
    is inferred from the filename passed via --file)
  ✓ No SUB or ATOMIC marker exists outside a PHASE marker
  ✓ No cross-nesting (PHASE→SUB→ATOMIC only, never deeper or reordered)
  ✓ No API-ID / XM-ID / TC-ID appears in more than one marker pair
    (catches grouped-ID violations — PROJECT-3-REGISTRY.md Section
    5.7.6 Rule 6)
  ✓ No duplicate marker ID within the file — this includes SUB markers,
    not only atomic ones: SUB:F1-SCR-ORG-001 and SUB:F2-SCR-ORG-001 are
    distinct and both pass; a bare SUB:SCR-ORG-001 repeated under two
    phases fails here (AMEND-P3-N, PROJECT-3-REGISTRY.md Section 5.7.5)
  ✗ Does NOT check content correctness, SUB-phase threshold
    correctness against actual entity/API/screen counts, or anything
    the generating engine's own self-check is responsible for —
    structural/marker validity only

Output: exit code 0 + "STRUCTURE VALID" on success; exit code 1 +
        a line-numbered list of every structural violation found
        (unmatched marker, illegal nesting, duplicate ID, non-canonical
        key) on failure. Treat any non-zero exit as blocking — fix the
        file and re-run before archiving it.

This mode does not archive, split, or write any package file — it is
read-only against the single file passed in.
```

## 5 — WORKFLOW (v2.0 — CHANGED: Agent 3 now runs TWICE, not once)

**Why twice:** the pipeline itself now has a real time gap between
Backend and Frontend (implementation + real API Docs happen in
between — see SHARED-GOVERNANCE-CORE.md CORE-2). Splitting/packaging
follows that same gap: Backend artifacts are packaged and ready for
the implementation agent right after P4.1 clears; Frontend artifacts
don't exist yet until much later, after P4.2 clears.

```

          PROJECT-3-REGISTRY.md Section 5.7 — no manual step required.
          The backend-test-plan.md is generated separately by the Test
          Generation Engine (after ALIGN-BE ✓), with the SAME markers.

          before archiving:

          Fix any reported structural error and re-run before
          proceeding to STEP 1. This is the mechanical counterpart to
```

(twice, not once) and the `--stage backend|frontend` flag are new.

(number of APIs/TCs)**. A module with 104 TCs (now split ~70
backend / ~34 frontend under v2.0's smaller per-file target counts)
still produces a handful of package files, not 104.

## 7 — GUARANTEES

```
GUARANTEE                          MECHANISM
──────────────────────────────────────────────────────────────────────
No content rewriting               Stage 2/3 do pure copy/paste from
                                    parsed block.content — no LLM call,
                                    no text transformation, anywhere in
                                    the splitting path.

No content loss                    Stage 5 computes SHA-256 hash of every
                                    atomic block (API/XM/TC) as it exists
                                    in the archived source, and compares
                                    it against the same block re-parsed
                                    from inside its package file. Any
                                    mismatch — even one corrupted word
                                    inside a 46-TC grouped file — is
                                    reported with the exact TC-ID and file.

Structural validity enforced       marker_parser.py rejects (with line
before any write                   numbers and clear messages) any
                                    unmatched START/END, illegal nesting,
                                    or duplicate ID, BEFORE Stage 2/3
                                    write a single file.

No silent partial archiving        Agent 2 reports exactly which files
                                    were found/copied/skipped; manifest.json
                                    tracks archived_files and skipped_files
                                    explicitly.

Approve-gated, resumable           Every stage in Agent 3 requires [y/N]
                                    confirmation. State is persisted in
                                    packages/_agent3-state.json — a failed
                                    or cancelled run can resume from the
                                    next incomplete stage without redoing
                                    completed work.

Module/version scalability         New modules: --auto-register flag
                                    registers them into modules-registry.json
                                    without editing code. New versions of
                                    an existing module: --new-version
                                    creates v2/v3/... alongside v1 without
                                    overwriting it.
```

## 9 — WHAT STAGE 2 DOES **NOT** DO

```
✗ Does not generate, rewrite, summarize, or validate governance CONTENT
  (that is exclusively the generating engines' responsibility —
  P(-1)–P4 for execution plans, the Test Generation Engine for tests).
✗ Does not enforce SUB-phase thresholds — it reads whatever the
  generating engine already produced. If the engine fails to apply a
  threshold correctly, Stage 2 will faithfully package the (possibly
  non-compliant) result as-is; it is not a structural auditor.
  (NOTE v3.0: the old "P4.1/P4.2 CHECK-4 structural audit" no longer
  exists — CHECK-4 was removed when P3 went light and test generation
  moved out. Threshold correctness for a test plan is now the Test
  Generation Engine's own self-check, and for an execution plan it is
  P3.1/P3.2's STRUCTURAL SELF-CHECK. Stage 2 substitutes for neither.)
✗ Does not call any LLM API — purely deterministic file/text operations.
✗ Does not replace P4.1/P4.2 (Governance Audit Engine, Backend/Frontend
  Gates). They audit CONTENT correctness and cross-artifact alignment
  of the execution plans; Stage 2 only verifies that packaging
  preserved content byte-for-byte.
✗ Does not modify backend-execution-plan.md, frontend-execution-plan.md,
  backend-test-plan.md, frontend-test-plan.md, or any other archived
  source artifact — archived copies are read-only inputs to Agent 3.
```
