# Workspace Architecture Reference

```
Document Type : Repository Structure Reference
Scope         : backend/ and frontend/ — two sibling git repositories
Status        : Clean-slate baseline — no prior module history
Stack         : Backend — Spring Boot (Java) | Frontend — React
                (TypeScript) + Vite + React Router + TanStack Query +
                React Hook Form + Zod
```

This is the single reference for "what exists, where, and why" across
the two repositories. Both repos are siblings on disk (e.g.
`~/projects/backend/` and `~/projects/frontend/`) — this document
assumes that layout without hardcoding a specific parent folder name.

```
════════════════════════════════════════════════════════════════
v3.0 NOTE — P3 LIGHT (test artifacts produced outside the pipeline)
════════════════════════════════════════════════════════════════
As of Project 3 v3.0, the execution-plan engines (P3.1, P3.2) produce
ONLY execution plans — no test artifact. The test artifacts that still
live at the P3_5_BE/ and P3_5_FE/ folders below (backend-test-plan.md,
test-execution-manifest.md, frontend-test-plan.md) are now generated by
the standalone Test Generation Engine (PROJECT-TEST-GENERATION-ENGINE.md),
which runs OUTSIDE the P0→P4 pipeline and consumes the light execution

Project 4 (audit) no longer reviews any test artifact (CHECK-4 removed).
════════════════════════════════════════════════════════════════
```

## 1. The Big Picture

```
backend/
  governance/     ← ALL governance content for EVERY module, both
                     backend AND frontend planning artifacts, lives
                     here except the two frontend-native exceptions
                     in Section 3
  src/            ← real Spring Boot application code

frontend/
  governance/     ← frontend-native governance content only (Section 3) —
                     small and deliberately scoped
  src/            ← real React application code (Vite project)
```

**Ownership principle:** `backend/` is where a module's governance
pipeline starts and where its backend implementation truth lives.
`frontend/` becomes an active governance participant only once a
module reaches its frontend planning stage — before that point, a
module has no footprint in `frontend/governance/` at all.

---

## 2. Ownership Rule (STRUCTURAL LAW)

```
RULE: Every module's governance artifacts live in backend/governance/
      by default. frontend/governance/ holds ONLY:
        (a) the frontend execution plan for a module that has reached
            that stage (natively generated there — never a copy), plus
            the frontend test plan (produced by the standalone Test
            Generation Engine, v3.0 — not by P3.2)
        (b) the frontend audit report for that stage
        (c) the frontend-side command/tooling files needed to drive
            frontend implementation from within frontend/ itself

RULE: master-registry.md and governance-tools/ (the Python tooling)
      are BACKEND-OWNED, always. frontend/ never has its own copy of
      either — it reads modules-registry.json from backend/ when it
      genuinely needs to (see Section 5), and never maintains
      master-registry.md at all.

RULE: No module's srs.md, db-script.md, or backend-execution-plan.md
      is ever duplicated into frontend/. frontend/ only ever holds
      frontend-native artifacts (frontend-execution-plan.md,
      frontend-test-plan.md) plus the two sanctioned cross-repo reads
      described in Section 5.
```

## 4. Where Each Governance Layer's Output Lives

```
P0     Platform Inception        → backend/governance/modules/<MOD>/P0/
P0.5   PRD Engine                 → backend/governance/modules/<MOD>/P0_5/
P1     SRS Engine                 → backend/governance/modules/<MOD>/P1/
P2     Database Engine            → backend/governance/modules/<MOD>/P2/
P2.5   UI/UX Design Engine (docs) → backend/governance/modules/<MOD>/P2_5/
P2.5   UI/UX Design Engine (mockups) → frontend/governance/modules/<MOD>/P2_5-mockups/
P3.1   Execution Plan — Backend   → backend/governance/modules/<MOD>/P3_1/
TEST-GEN  Backend Test Plan + Manifest → backend/governance/modules/<MOD>/P3_5_BE/
          (standalone Test Generation Engine — outside the pipeline, v3.0)
P4.1   Backend Audit              → backend/governance/modules/<MOD>/P4_1/
        ── UI Shell implementation happens here, in frontend/src/,
           BEFORE the next two stages — see CLAUDE.md's UI Shell
           Implementation Protocol ──
P3.2   Execution Plan — Frontend  → frontend/governance/modules/<MOD>/P3_2/
TEST-GEN  Frontend Test Plan       → frontend/governance/modules/<MOD>/P3_5_FE/
          (standalone Test Generation Engine — outside the pipeline, v3.0)
P4.2   Frontend Audit             → frontend/governance/modules/<MOD>/P4_2/
```

The split between "docs" and "mockups" for P2.5 is the only artifact
type that crosses repos — its governing text (`flow-diagram.md`,
`ui-ux-spec.md`) stays with the rest of the module's planning trail in
`backend/`, while its rendered visual output (`visual-mockups/`) lives
in `frontend/` where a developer building the UI Shell will actually
look for it.

Note (v3.0): the Test Generation Engine writes into P3_5_BE/ and
P3_5_FE/ (the same folders as before) even though it is not a numbered
pipeline stage — it consumes the light execution plans from P3_1/ and
P3_2/. Project 4 never reads these test folders (CHECK-4 removed).

## 5. Sanctioned Cross-Repo Reads (the only two — nothing else)

```
1. frontend/.claude/commands/generate-module-setup.md reads
   backend/governance/governance-tools/modules-registry.json in its
   Step 0, purely to look up module metadata. It does not write to it,
   and modules-registry.json itself is never duplicated into frontend/.

2. frontend-side execution reads real API Docs from
   backend/governance/modules/<MOD>/api-docs/ (generated by
   api-doc-generator from the live backend) — this is how F2's
   TanStack Query hooks and F4's route/component documentation confirm
   themselves against the real, implemented API surface (CONTRACT-12).
```

No other `../backend/...` or `../frontend/...` path reference is
permitted anywhere in either repo's tooling or command files. This is
enforced by the periodic tooling audit (see
`WORKSPACE-GOVERNANCE-AUDIT-PROMPT.md`, CHECK-5).

## 6. Why frontend/ Generates Its Own Source

```
Project 3.2 (Execution Plan — Frontend) runs AS ITS OWN PASS, gated on
GATE: BACKEND MODULE COMPLETE + GATE: UI SHELL COMPLETE — never before
those two gates confirm. Once it starts, its output
(frontend-execution-plan.md) is generated NATIVELY inside
frontend/governance/modules/<MOD>/P3_2/ — there is no backend-owned
"master copy" of this content anywhere for frontend to reference or
copy. Same for frontend-test-plan.md (P3_5_FE/, produced by the
standalone Test Generation Engine, v3.0) and the P4.2 audit report
(P4_2/).
```

`agent3_splitter.py --track frontend` runs from `frontend/`'s own
tooling, splitting `frontend-execution-plan.md` /
`frontend-test-plan.md` into `packages/frontend-execution/` and
`packages/frontend-test/` — entirely within `frontend/`, never touching
`backend/` at all.

## 7. The UI Shell Step — Where It Lives and What It Touches

```
Timing  : After Project 2.5's mockups are human-approved, BEFORE
          Project 3.2 (frontend-execution-plan.md) begins.
Where   : frontend/src/ — real application code, real components,
          real routes.
Reads   : backend/governance/modules/<MOD>/P2_5/flow-diagram.md +
          ui-ux-spec.md (governing intent) +
          frontend/governance/modules/<MOD>/P2_5-mockups/ (visual
          reference)
Writes  : Real React components + React Router route definitions in
          frontend/src/features/<module-kebab>/ — presentational only,
          no data binding, no service/hook wiring yet.
Gate    : GATE: UI SHELL COMPLETE — a human sign-off, separate from the
          mockup approval itself, recorded before Project 3.2 may begin.
```

This step touches only `frontend/src/` — it does not read or write
anything under `backend/`, and it does not touch
`frontend/governance/` either (that only starts accumulating content
once Project 3.2 actually runs, afterward).

## 9. Quick Answers to Common Questions

**"Where does a new module's SRS live?"**
`backend/governance/modules/<MOD>/P1/srs.md` — always, no exceptions.

**"Where does a new module's frontend execution plan live?"**
`frontend/governance/modules/<MOD>/P3_2/frontend-execution-plan.md` —
generated there natively, once both gates in Section 7 have passed.

**"Where do the test plans come from now?"**
The standalone Test Generation Engine (PROJECT-TEST-GENERATION-ENGINE.md),
outside the pipeline. It consumes the light execution plans and writes
backend-test-plan.md + test-execution-manifest.md into P3_5_BE/ and
frontend-test-plan.md into P3_5_FE/. P3.1/P3.2 no longer produce these,
and P4 no longer audits them (v3.0).

**"Can I start frontend work before the backend is fully built?"**
The UI Shell step (Section 7) can start as soon as mockups are
approved — it doesn't need the backend built. But
`frontend-execution-plan.md` (Project 3.2, F1-F4) cannot start until
`GATE: BACKEND MODULE COMPLETE` also confirms — see CONTRACT-12 in
`shared-artifact-contracts.md`.

**"What if I need something not covered above?"**
Stop and ask. Do not invent a new location or duplicate a source of
truth silently.
