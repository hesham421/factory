P2 written for NOTE v1.

**Files**
- `erp/modules/NOTE/P2/db-script-note.md` — header · DBF matrix · XM register · FULL_DATABASE_SCRIPT (blocks 1–11) · decisions · registry pointer · DBF index · RULE→constraint map with the C6.9 data-source binding.
- `erp/modules/NOTE/P2/registry-db-note.md` — registry.
- `erp/decisions/NOTE/ADR-NOTE-004.md` — the one ambiguity self-resolved (index strategy), ACCEPTED / non-breaking, pass continued.

**Structure** — 1 table `NOTE_NOTE` (ENT-NOTE-001), 9 DBF (`DBF-NOTE-001 … 009`), 0 XM. PK generation is `sequence`: `SEQ_NOTE_NOTE` in BLOCK 1, `note_pk BIGINT NOT NULL` with no identity clause and no sequence default anywhere. Three CHECKs (non-blank title, body, owner), no UNIQUE (the SRS declares no business key), no FK of any kind, no trigger, no seed data (A6: the module owns and consumes no lookup key), three owner-leading indexes.

**Two judgment calls worth flagging:**
- `noteTitle` / `noteBody` are logical type `text`, which §4.1 maps to `TEXT`, but both carry declared maxima (RULE-NOTE-003 / ADR-NOTE-002) — emitted as `VARCHAR(200)` / `VARCHAR(4000)` with a governance note, since a `TEXT` column could not carry the limit.
- XM count is zero by SRS A8's own classification (identity as a principal string, registration rows as deployment data, precedent ADR-FIN-001). Inventing an XM row here would be an orphan under §5, so BLOCK 11 is empty by construction.

Note that SEC's P2 script uses `GENERATED ALWAYS AS IDENTITY`; this brief forbids it and mandates `sequence`, so NOTE differs from SEC on PK strategy. That's a cross-module inconsistency in the platform, not something this stage can correct.
